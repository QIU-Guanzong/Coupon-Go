# Coupon-Go 商家工作台與子頁操作設計

基線：main `e1c4fb3bc6556df70e4ab0cdc74bb946a5edd615`。V7 #56 與 L1–L17 繼續處理排版；本稿處理路徑、操作回饋和資料口徑，不重做元件。只提交設計，不改 API、交易、價格、權限或結算，也不部署。

## 第一屏：先讓人找到能做的事

保留企業版底欄，不加第五或第六項。從現有「主頁」進整合工作台：上層是店舖範圍與「掃碼核銷」「管理優惠」，下層是「顧客評價」「經營數據」及各自的最近摘要。多店保留已選店舖；單店不用經過選店頁。店舖切換若會丟失表單，先保留輸入或確認離開；舊店請求不得更新新店。客服與收款設定留在帳戶頁，工作台不混入收款。

用可返回、可重試的子頁代替多層彈窗。子頁返回原卡片、篩選和滾動位置；成功只刷新受影響的資料。深連結先解析登入、角色與店舖；未授權不顯示其他店資料。「更新中」可以保留同店、同查詢的上一筆結果；切換店舖或帳戶先清空。載入、無結果、網絡失敗、權限不足各有明確去向。表單保留填寫內容，進行中禁止重複提交；請求結果不明時先核對，不先宣告成功或盲目重送。繁中、英文用相同資訊層級；可按的區域至少 44×44，手機可在 130% 字體大小下操作。

## 1. 顧客評價：從店舖總覽到回覆

**路徑**：工作台 → 顧客評價 →（多店才選店）→ 評價列表 → 評價詳情／回覆 → 返回同一條評價。列表顯示星級、日期、評價摘要與回覆狀態；「最新」「最有幫助」沿用已有排序。「待回覆」與「低評分」等全店計數、篩選須等服務端支援；不能拿第一頁的總數充當全店，也不能只篩第一頁就顯示「沒有待回覆」。既有回覆帶入編輯框；送出後依回傳的 review 更新該項。失敗時保留文字，讓店主可以重試。

**可直接用**：`GET /shops/{shop_id}/reviews`（`page`、`has_images`、`sort=latest|helpful`）、`GET /shops/{shop_id}/rating`、`POST /reviews/{review_id}/reply`。現有 `MerchantReviewShopPicker` 和 `MerchantReviewReplyScreen` 可逐步重用；商家回覆目前走預設第一頁，公開列表只含 visible。服務端允許店主／管理員回覆，店員雖可看不因此取得回覆能力；入口以既有權限為準。

**後端後續**：新增商家店舖範圍內的工作列表與按狀態分頁（提案 `GET /merchant/shops/{shop_id}/reviews`），回傳列表、待回覆總數及 `can_reply`／`can_dispute`。申訴已有 `POST /reviews/{review_id}/dispute`，但申訴後評價會自公開列表移除及暫不計星級；商家端不可因此看不到自己的申訴進度。在私有列表可讀到待審狀態之前，不新增無法回查的商家申訴入口。顧客側仍用自己的評價表單與公開列表。

## 2. 核銷：掃描、核對、確認、回查

**路徑**：工作台 → 核銷 → 掃碼／手動輸入 → 核對優惠與使用分店 → 確認 → 成功憑證，可去記錄或繼續核銷。進入核對即暫停掃描，避免同一碼重複觸發；切換分店須重新核對。結果頁顯示已核銷內容、時間、分店和記錄入口。過期、已使用、分店不適用各自顯示下一步，不顯示通用成功。查找／補錄與批次是分開的入口，普通撤銷和管理員強制撤銷不共用提交按鈕。回查只顯示手機末四碼等既有遮罩資料。

**可直接用**：`POST /new-scan-coupon/prepare` → `POST /new-scan-coupon`；分開沿用 `/new-scan-coupon/batch`、`/merchant/redemptions/lookup`、`/merchant/redemptions/supplementary-scan`、`/redemptions/{id}/revoke`。批次按現有服務端合約整批成功或回滾，同一批重試使用原 `idempotency_key`；不把批次的可重放性套給普通核銷。普通請求逾時先回讀記錄，未建立穩定對應時保留「查看核銷記錄」而不自動重送。不可回退至本地核銷或無準備的重送。

**已核對的缺口**：`vendorRedemptions()` 現在從 export 拉資料再在 Flutter 篩日期，下載 CSV 並無相同條件；服務端其實已支援 `from/to/coupon_id/revoked/method`，應由同一查詢物件供清單與下載，顯示清楚正在匯出的範圍。現有查詢以時間戳的日界線過濾；若要對外宣稱香港時間，先在服務端定義與測試 UTC+8 換日，再同步記錄、下載及看板，勿只轉顯示字串。服務端還未提供分頁式記錄查詢；先復用既有篩選，再以單一店舖權限查詢補分頁，不長期用 export 路徑載全部資料。

## 3. 優惠管理：把狀態與下一步放同一頁

**路徑**：工作台 → 管理優惠（優惠券／套餐）→ 按店舖、狀態找商品 → 商品詳情 → 編輯／提交審核／暫停／恢復／下架。詳情頁第一屏放目前狀態、可售時間、剩餘數量與一個主要操作；低頻操作進更多選單，下架要說明對新客的影響並確認。提交按實際返回顯示「待審核」「已排期」「已上架」，不用固定成功文案。並行改動或頁面過期時，以服務端最新商品為準，刷新後讓商家重新選操作。

**可直接用**：`GET /get-vendor-coupon-list?status=`、`GET /vendor/package-workspace`、券與套餐的 `POST .../{id}/pause|resume|unlist|submit`。服務端會校驗草稿、待審、排期、售罄、過期；套餐是否重新審核由現有配置決定。沿用券狀態更新校驗（回應 ID 和狀態）；套餐 UI 也應校驗後才更新卡片。套用共用 pill 和確認區塊，不合併兩套業務狀態機。已購套餐用凍結模板，依後端條件仍可用；不要從下架狀態推斷其退款或失效，也不要在未有券證據時泛化其承諾。

## 4. 調價：先把影響講清楚，再開放寫入

商品詳情的「價格」開獨立編輯頁：目前已生效價、新價、差額、何時生效、可能重新審核；產品應清楚分開券面優惠價 `discount_price`、券售價 `sale_price`、套餐售價 `package_price`。下一步先放唯讀對比原型，不上真正的調價入口。任何可改客戶付款或結算金額的改動，在實作前先有獨立 PR 寫清：支援的商品、歷史訂單／券如何凍結、審核策略、衝突處理、回滾及會計口徑。

已有 `PATCH /vendor/coupons/{id}`、`PATCH /vendor/packages/{id}`。套餐模板凍結與在途訂單的保障有文件；不推定普通付費券已有相同保障。方案建議先讓套餐價格修改與付費券修改分開驗證；服務端權威校驗價格、幣別、精度和商品版本，衝突回傳最新值並保留輸入（版本前置條件、改價收據和操作記錄屬待設計契約，不能當現成功能）。不可回寫舊訂單、優惠快照、退款或佣金。

## 5. 經營數據：前端畫圖，後端掌握口徑

工作台先給「核銷張數／領券轉化」，點「經營數據」看全店／選店、7／30／90 日和按券表。全店現有接口給的是總量與各店對比，單店才有日趨勢及按券。空期間顯示沒有記錄；資料缺項不當 0；分母為 0 時顯示不適用。讀取失敗保留同查詢上次資料並可重試。收款餘額、可提款與待結算留在帳戶，不和營運「結算基數」混成收入。圖表應有鍵盤可讀的表格，手機不用橫向拖整頁。

**可直接用**：`GET /merchant/dashboard?days=`、`GET /merchant/shops/{shop_id}/dashboard?days=`。來源字段保留 `redemptions`（排除撤銷／缺有效結算基礎者）、`claims`、`redeemed_claims`、`redeemed_orders`、`gross_amount`／`commission`／`net_amount`。轉化是同窗領且核銷／同窗領，客單按已核銷訂單去重；兩者均不平均不同店的百分比。今日口徑必須從後端經過日界線測試再改，不用 Flutter 按手機時區重算。對帳直接連既有餘額及明細，不改提領條件。

**後端後續**：先定義 HK 日界線與返回的 time zone／區間、最近生成時間；再加可選的全店趨勢，不在客戶端逐店扇出及相加。測比較 23:59／00:00 HKT、跨日核銷、撤銷、付費與免費、同單多張、無訂單、缺歷史證據。評價走獨立統計，暫不影響核銷或營收數。

## 開發順序與驗收

| 批次 | 首次交付 | 必驗用例 |
|---|---|---|
| A | 工作台入口、返回狀態、評價列表和回覆 | 單店直達、多店切換、分頁、權限切換、回覆失敗保留文字及成功後同列更新；舊店的慢回應不覆蓋新店 |
| B | 普通核銷三步、記錄同條件匯出、上架狀態詳情 | 快速重掃、分店變更、逾時、已核銷、批次重播／整批回滾；暫停、恢復排期、售罄、撤下後舊套餐可按既有規則核銷 |
| C | 看板只讀指標和單店下鑽 | 全店／單店 7、30、90 日；零分母、無資料、跨店競態、核銷與表格對數；後端香港換日成獨立合約測試 |
| D | 調價唯讀原型，另提金額變更方案 | 雙擊與併發、舊待支付訂單、舊券及退款不漂移；上述證據齊全才考慮寫入 |

每段先用 Flutter widget/integration 以假資料驗返回路徑及錯誤態，再走隔離商家與顧客入口；有寫入者只用隔離測試庫與種子，不操作正式交易。先跑本地 `flutter analyze`、相關 `flutter test` 和 API 合約／資料庫測試；390×844 中英、130% 字體、大屏各留證據。路由或 JSON 改動同步更新 `docs/API.md`。不為設計稿觸發 Actions。
