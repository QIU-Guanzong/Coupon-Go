# PR #11–#20 审计与合并顺序（2026-11-21）

基线：main @ 3f2d8bc。10 个 PR 全部直接基于 main，约 1.7 万行改动，互相重叠。测试结果见文末。

## 一、总判断

每个 PR 单独看，描述详细、测试齐全，大部分功能设计也合理。**真正的风险在整合，不在单个功能：**

1. **迁移编号撞号：** 7 个 PR 同时声称 0021（#13、#14、#15、#16、#18、#19、#20），#11 用 0022 接在 #13 后面，#17 用 0023。按现状合并任意两个，数据库迁移链就会出现多个头，`alembic upgrade head` 直接报错。
2. **同一批热点文件被多方改动：** `models.py`（8 个 PR）、`routers/coupons.py`（7 个）、`routers/packages.py`（5 个）、`schemas.py`、`scheduler.py` 等。
3. **同一个函数被写了两遍：**
   - `_redeem_item()`（核销唯一链路）：#12 和 #15 各写了一份；
   - 积分政策层：#12 的 `app/points.py` 和 #20 的 `points_service.py` 各一套；
   - `Coupon.sale_price`、`refund_policy`、「付费券不可免费领」：#14 和 #18 各加一遍；
   - 商户余额与提款：#16（Stripe Connect 流水）和 #19（结算单为基础的提款申请）是两套互相矛盾的设计；
   - 调度器任务编号和锁号：#12、#14、#19 都认领「第 5 个任务」，#12 和 #14 的锁号冲突。
4. **审批人没人拍板：** 各 PR 都写「合并顺序等 Miso 裁决」。下面就是裁决结果。

## 三、逐项审计

### 3.1 #13 M9-7 真删号 — 不合格（阻塞）

已有：可提现返现时拒绝删除；未使用券作废；积分清零；软删除记录时间。

**缺的，也是我之前发的 M9-7 单子里明确要求的：**
- **删号后可被复活：** 我实测了：注册 → 删除 → 对同一邮箱重发验证码 → 验证，返回 200，之后用原密码登录成功。任何能收到该邮箱邮件的人都能让「已删除」的帐户恢复。
- **同一邮箱不能重新注册：** 删号后用同一邮箱注册返回 400「此電郵已註冊」。
- **个人资料没有匿名化：** 邮箱、姓名、电话原样保留。App Store 要求的是真删除。

**要求：** 删除时匿名化个人资料（邮箱改成不可用的占位值，姓名、电话清空，密码哈希作废）；重发验证码、验证、忘记密码都拒绝已删除帐户；允许用原邮箱重新注册成一个全新的帐户；登录时给已删除帐户单独的提示；补上述四条测试。商户帐户还要处理：名下有在营店铺或未结算款项时拒绝删除。

### 3.2 #11 P1-D 商户入驻

我上一轮提的返工，muse 已推送（提交 e9132c8）：中文字体缺失时拒绝签约、上传限额与频率限制、文件头校验、可信代理 IP、日志不记查询串、存储收成接口。抽查代码与描述一致。

我在本机复跑：6 个测试失败，原因都是本机没有安装中文字体（`fonts-wqy-zenhei`），签约接口按要求直接返回 503 拒绝生成残缺 PDF，这是预期行为。CI 里要装这个字体（我已加到 PR 21 的 CI 里），装好后需确认全绿。

仍要做：rebase 到最新 main、迁移号改为 0025、与 #17 合并批准流程（批准 = 已签当前合约 + Stripe 开户完成 + 自动建店，同一事务）。

### 3.3 #16 P1-B Stripe Connect — 不合格（涉及真金白银，阻塞）

设计方向对：核销后转帐、佣金按店设定、不存银行帐号、未配置时拒绝（fail closed）、只接受测试密钥。但有三处会导致多付钱：

1. **没有幂等键：** 转帐、冲回、提款的请求都没带 Stripe 的 Idempotency-Key（我在 `connect_gateway.py` 搜了，没有）。请求超时但 Stripe 实际已执行时，重试会再转一次，商户收到两份。每笔请求必须带固定的幂等键（如 `transfer-{流水id}`），Stripe 看到同一个键会返回原结果。
2. **提款可以并发重复：** `request_payout` 先读余额、再调 Stripe、最后才写流水，中间没有锁。同一商户同时点两次提款，两次都通过余额检查，可提走两倍。必须先锁住该商户的帐户行，先写一条「处理中」流水扣减余额，再调 Stripe，成功后改为已付、失败则回滚。重试转帐的接口也有同样的并发问题。
3. **转帐在核销事务里同步调用 Stripe：** 核销事务还没提交就发起网络请求。Stripe 成功但数据库提交失败，会出现钱已转出、却没有核销记录和流水。应该改为：核销事务里只写一条「待转帐」流水并提交，由调度器任务（或提交后的回调）去转帐，失败自动重试，幂等键保证不重复。

**其它：** Stripe 开户使用的是带 `preview` 字样的 API 版本（2026-11-18.preview）。预览版本可能变更，用于生产前必须在 Stripe 文档确认是否已正式发布，并写进版本升级流程。冲回失败（商户已提走钱）时的坏账处理规则没有定，需要运营规则：余额可为负数，并停止该商户后续提款，直到补足。

### 3.4 #14 上架审核流程 — 需要产品决策

最大的改动是：**所有套餐创建后变成「待审核」，要管理员批准才上线**（之前是直接上线），改券也要重新审核。功能本身合理，但：Flutter 没有任何套餐审核的界面，商户在 App 里建了套餐就石沉大海。合并前选一：
- 先给管理员做审核界面，再合并（dot 的工作）；
- 或加开关 `LISTING_REVIEW_REQUIRED`：体验环境和早期默认关（自动批准），正式运营再开。**我推荐这个。**

另：与 #18 重复定义 `sale_price`，以 #14 为准，#18 去掉。迁移里把负库存改成 0，是数据修改，要在发布说明里写明。

### 3.5 #18 P1-A 付费券 — 基本通过，需 rebase

复用订单链路，价格取自服务器上的券，不信客户端；加了行锁、幂等重放、售罄回滚、退款和超时释放；付费券禁止免费领取。需注意：
- GitHub 显示它与 main 有冲突（需 rebase）；
- 积分兑换接口（`/points/exchange`）没有挡付费券，若有券同时标了「积分兑换」和售价，可以免费换到；加一条校验并补测试；
- 去掉与 #14 重复的部分，迁移号改为 0023。

### 3.6 #20 P1-C 积分按消费 — 通过，小修

规则对：付费核销按实付金额 × 倍率向下取整、12 个月过期、退款扣回、余额为负时禁止兑换。要改：
- 在 #12 的 `points.py` 里实现，不另建一套；
- 过期清理每 5 分钟会读出所有用户的全部积分流水再逐个算，用户多了会越来越慢，改成只查有「已到期且未被消耗」积分的用户，并给 `expires_at` 加索引；
- 砍价购买的券（没有订单）按固定 20 分发放，而它是付过钱的，需要你定：砍价也按实付金额发分，还是维持固定值。

### 3.7 #19 统计看板与提款 — 部分保留

保留：经营看板、月结算自动生成（每月 1 日）、逐行口径说明、商户发起异议、CSV 导出、对账改按金额校验。

**不保留：** 「商户提款申请 → 财务批准 → 执行打款」这套。你已决定走 Stripe Connect（核销后即转帐，商户自己提款），而 #16 已是这个设计；#19 另有一套以月结算单为基础的「可提取余额」，两个余额口径会互相打架。改为：余额和提款只用 #16 的；月结算单留作对帐记录。

### 3.8 #12 unify、#15 核销、#17 商户管理

- **#12（无迁移）：** 把券、套餐、砍价的购买、核销、退款、统计口径收到共享函数，有 21 个新测试，我看过描述和接口清单，行为变化只有它列出的两处。是基础重构，应该第一批合并（在 #13 之后），否则后面所有 PR 都要重改。
- **#15：** 内容有用（找回券码、事后补核销、强制撤销、批量核销，均写审计日志）。但它自己实现了一份 `_redeem_item()`，与 #12 的同名函数冲突。要求在 #12 合并后重写成调用同一个函数。PR 里自述全量测试有 19 个失败，归因于并行共享临时库；我单独复跑全量 365 通过、0 失败，印证了这个解释，但测试隔离仍要修。
- **#17：** 自动建店、分店、四级店员权限、门店资料自助维护、商户站内通知。功能合理；迁移号需要改，批准流程要与 #11 合并。
