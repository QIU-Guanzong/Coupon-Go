1. 按下表顺序，**一次只让一个 PR 进入「可合并」状态**。前一个合并后，下一个才 rebase 到最新 main、重新取迁移号、重新全量测试。

3. 每个 PR 的 CI（SQLite 全量）要通过；Postgres 并发测试在 PR 里附日志。
4. 测试共享 `/tmp/*.db`，并行跑会互相覆盖（#15、#19 都因此出现过假失败）。给每个测试库用独立临时目录（`tmp_path` 或 `M6_TEST_DB` 这类环境变量），不要再靠「隔离后复跑」自证。

## A. #13 M9-7（阻塞）

我在 PR 分支上实测：注册 → 删号 → 重发同邮箱验证码 → 验证返回 200 → 原密码登录成功。删号可被复活。必须：
1. 删除时匿名化：邮箱改成不可用的唯一占位（如 `deleted+{user_id}@invalid`），姓名、电话清空，密码哈希作废；保留 `deleted_at`、用户 id 和所有账本、审计行。
2. `/new-resent-otp`、`/resent-otp`、`/new-verify-otp`、`/password/forgot`、`/password/reset`、登录对已删除帐户一律拒绝（登录返回单独提示「此帳戶已刪除」）。
3. 原邮箱可以重新注册成全新帐户（匿名化后邮箱即空出）。
4. 商户帐户：名下有在营店铺、未结算款项或进行中订单时返回 409 说明原因。
5. 测试：复活攻击失败、同邮箱重新注册成功且数据不串、商户被拒、匿名化字段断言。

## F. #16 P1-B Stripe Connect（阻塞，涉及真金白银）

1. **幂等键**：`create_transfer`、`reverse_transfer`、`create_payout` 的 Stripe 请求都带 `Idempotency-Key`，键由库里的流水 id 派生（如 `transfer-{entry_id}`、`reversal-{entry_id}`、`payout-{entry_id}`），重试用同一个键。测试：模拟「第一次请求超时但 Stripe 已执行」，重试后只产生一笔。
2. **提款并发**：`request_payout` 先对该商户帐户行加行锁（`SELECT ... FOR UPDATE`），在锁内算余额，**先写一条「处理中」的提款流水扣减余额并提交**，再调 Stripe；成功改「已付」，失败改「失败」并释放余额。同一商户并发两次提款，总额超过余额时必须有一次被拒。Postgres 真并发测试。`retry_transfer` 同样要锁定那条流水。
3. **转帐不在核销事务内调 Stripe**：核销事务里只写「待转帐」流水并提交；转帐由调度器任务（`connect-transfers`，批量、有上限）和手动重试接口执行，用第 1 项的幂等键。失败只更新备注与重试次数，超过 N 次进入「需人工」状态并给 admin 通知。核销接口不再受 Stripe 延迟影响。
4. **校验与权限**：请求体改用 Pydantic 模型（现在是裸 `dict`）；提款、重试限定店主（`merchant-admin`）与财务角色，收银员和店长不可提款（#17 的角色体系合并后）。
5. **Stripe 版本**：确认 `2026-11-18.preview` 是否已正式发布；若仍是预览，在 PR 里写明风险、固定版本的理由与升级流程，并做成配置项，不要写死。
6. **冲回失败**（商户已提走）：规则写进 `docs/P1B_API.md`：该商户余额可为负，负数时停止新提款，admin 看板有「待追回」列表。加测试。
7. 金额一律用 `Decimal` 转分，不经过 `float`。
